# 地形和放置：引擎怎么读、我们该怎么写

引擎线第 6、7 轮（2026-11-04）。依据 ADR 0017（按层逆向，先放置和通行，再地形）。写法照 `script-semantics.md`：**码** = 读了游戏程序；**测** = 测试台；**推断，未实测** = 只从数据或别的资料推出来。反编译细节只在 `work/re/`（不进仓库）。

规则落成了纯函数 `experimental/campaign/terrain_rules.py`，测试在 `tests/test_platmap_terrain.py` 后半段（原 `tests/test_terrain_rules.py`，为守卫 G4 并进来的）。外壳线做地形编辑（抬高、压低、整平、画通行）时直接调它。

## 1. 高度的单位（码）—— 和我们的代码对不上

- 地图里 `HeightMapData` 每格存一个 16 位数。游戏把它乘 0.0390625（即 ÷25.6）当成世界高度；格子 10 个世界单位宽，第 (i, j) 格的点在 ((i − 边框) × 10, (j − 边框) × 10)。很老的版本（v4）存 8 位数，读进来乘 16。
- 我们的代码（`mapterrain.SCALE = 16`、`platmap.TIER`、`STEEP`、`FLAT`、`newmap.WATERLINE`）一直把"存储值 ÷16"当成世界高度。**真实世界高度 = 我们的数 × 0.625。** 所以：
  - `platmap.FLAT = 8` 实际是 5 个世界单位；`STEEP = 9` 每格实际是 5.6／10，约 29°；`TIER` 的层高 115 实际是 72。
  - `newmap.WATERLINE = 285.7` 实际是 179 世界单位。地图里的水面写的是 200 世界单位（`GlobalWaterSettings` 和 `StandingWaterAreas` 都是 200），按游戏的换算就是我们的 **320**。
  - **游戏逻辑上的水面就在 320 附近**（测，第 9 轮，`checks/engine_bits.py` 的 `water`）：四个圈外面各挖一圈沟，沟底分别在我们的 270、300、315、330（世界 169、187.5、197、206），坦克和武士都过不去前三道、过得去 330 那道。所以 315 的沟底在游戏里算水，330 算干地，和"水面 200 世界 = 我们的 320"一致。`mapterrain.py` 开头记的"285 以上才露出水面"是画面上看的，逻辑上不对（画面是不是这样，没再看）。
  - **关卡线 / 地图线该怎么改**：我们的代码把 285.7～320 这一段当干地（`newmap.WATERLINE`，`platmap.lint` 的"干地"是它 +10，即 295.7），游戏却当水：坡道、海滩、桥头落在这一段，地面单位走不上去，建筑也放不下（水里）。要把"干地"的判断改成 ≥ 320 再留几个单位余量（例如 330）；已有地图要跑一遍 lint 看有没有站点、坡道、桥头落在 285.7～330 之间。`WATERLINE` 同时管贴图（沙滩、海底），改它会改地图的样子，所以建议新加一个逻辑水线常量，贴图那条先不动。
- 我们地图内部自洽（高度、坡、水线都在同一套单位里量出来），所以**不用改已有地图**；只有拿游戏数据里的数字（建筑允许高差、射程、几何尺寸）来比时要换算：`terrain_rules.world()` / `ours()`。

## 2. 改了高度，哪些要一起改

按 `platmap.apply`（现有的写图函数）的顺序，`terrain_rules.MUST_FOLLOW` 列着：

1. `HeightMapData` 的存储值：我们的数 × 16 取整，夹在 0～65535。
2. `BlendTileData` 第 0 个位图（不可通行）：在改动的格子**和外面一圈**重算（一个格子的坡度看它上下左右四个邻居）。`terrain_rules.apply_edit()` 只重算这块，别处手画的保留。
3. 地表纹理（陡处换岩石）：只管好看，游戏判断能不能走不看纹理（测，第 3 节 `engine_terrain walk`）。
4. 雷达小图：只管好看。
5. 物件和路点的 z **不用动**：它是"离地多高"，不是绝对高度（推断，未实测：我们的全是 0；27 张原版战役图 160711 个物件里 96% 是 0，其余是栅栏抬 4 之类的小数，如果是绝对高度它们会埋进地里）。
6. 设计检查：`Site.build` / `Site.cast` 的方块、坡道 `RAMP_MAX`、水边，跑 `platmap.lint`。

## 3. 能不能走（通行）

- 我们的写法：干地上坡度（到四邻的最大高差）超过 `STEEP`（我们的单位 9／格）就置"不可通行"位；水面以下不置位，交给水域。`terrain_rules.passable()` / `impassable_bits()` 就是这条，测试把它和 `platmap.walkable`、`platmap.apply` 绑在一起，免得编辑器和生成器各算各的。
- `BlendTileData` 的 8 个位图按文件顺序是：不可通行、玩家不可通行、通道宽度、额外可通行、可见、可建造、空军不可通行、泰矿可生长（`terrain_rules.FIELDS`）。名字按别的 SAGE 读图程序对 v27 的读法和原版图的统计（第 0 个在陡坡、第 4 个约 94%、第 5 个约 2%）定的：**推断**；第 0、1 个已实测对得上，第 6 个没对上，见下面"其它几个位图"。我们的生成器只写第 0 个，第 4 个全开，其余全关。
- **游戏只信第 0 个位图，不自己按坡度算悬崖**（测，第 9 轮，`checks/engine_terrain.py` 的 `walk`）。探针地图 `maps/probe_ground.py` 上四个圈，圈里各放一辆守护者坦克、一个帝国武士，命令走到圈外 260：
  - 陡坡没标位（墙高 80，每格升 40，约 68°）：坦克、步兵都翻过去了；
  - 平地标了位（一圈 60 宽的平地）：都出不去；
  - 两个对照（陡坡标了位、平地没标位）：出不去、出得去。
  - 地表纹理四个圈都是草：纹理不影响能不能走。
- **关卡线 / 外壳线该怎么做**：
  - 改高度的工具一定要跟着重算第 0 个位图（`terrain_rules.apply_edit()`）。只改高度不改位图，陡坡会变成谁都能爬的坡，平掉的悬崖仍是一堵看不见的墙。
  - 反过来，第 0 个位图可以当"看不见的墙"用：在平地上画一道就能封路。但玩家看不出为什么过不去，要配上看得见的东西（栅栏、碎石、悬崖纹理），别只画位图。
  - 我们现有的生成器（`platmap.apply`、`newmap`）本来就按坡度写了位图，已有地图不用改。
- **其它几个位图**（测，第 9 轮，`checks/engine_bits.py` 的 `bits`，探针地图 `maps/probe_bits.py`）：一圈 60 宽的平地上只标某几个位图，圈里放两个单位，脚本命令走出去：
  - **第 1 个就是"玩家不可通行"**：玩家的坦克、武士都出不去；同样的圈，敌方（`Soviet_1`）的坦克、武士都出去了。
  - **第 0 个加第 3 个**：照样出不去——第 3 个不能把第 0 个封住的地方重新打开（第 3 个是什么，没查出来）。
  - **第 6 个**：玩家的冰冻直升机和坦克都出去了。所以它至少不挡地面单位，也不挡直升机按脚本移动；"空军不可通行"这个名字没得到证实（推断，未实测：也许只管飞机落地或者 AI 选路）。
  - 第 2、4、5、7 个没测。
- **关卡线该怎么用第 1 个位图**：它能做"只挡玩家、不挡敌人"的墙——敌人的援兵、进攻队、脚本单位从玩家进不去的地方出来或者穿过去（例如后巷、地道口、界外的出兵道）。和第 0 个一样看不出来，要配看得见的东西。玩家的单位被脚本命令也照样挡住，所以别把玩家的车队路线画进去。第 6 个别指望拿来限空军：限空军还是靠防空或者剧情。

## 4. 能不能放（建筑、施法）

- 建筑放置允许的高差是全局设置 `BuildSystemSettings.AllowedHeightVariationForBuildingPlacement`，默认 **3 个世界单位**（= 我们的 4.8）；原版的设置文件没改它（码：数据和格式定义）。`platmap.FLAT = 8`（= 5 世界单位）比它松。`terrain_rules.flat_enough()` 按 3 判。游戏在脚下取哪些点来量高差：没读出来（判断藏在建造者模块的虚函数后面；程序里的"放置网格"只管吸附，每格 30 世界单位，不管合法性）。我们的函数取整个方块的所有格点，比游戏怎么取都严，所以关卡线不用改。
- 基地扩展范围另有一个高差 `AllowedBuildabilityHeightVariation`（默认 50），是"建造范围圈"能盖住多陡的地，不是建筑本身。
- 冰幕工兵的冻冰墙是 `AssembleStructure`（工兵走过去盖一个小建筑），所以玩家放冰墙走的是**建筑放置**这一套：上面的高差、`PATHABLE_ONLY`、`ForbiddenObjectRange=32` 都算。脚本 `NAMED_FIRE_SPECIAL_POWER_AT_WAYPOINT` 不检查位置（第 1 轮，码）。
- **后巷口 V1**（关卡线 K3）：**关卡没问题，是测试台点偏了**（测，第 8 轮）。
  - 现象：测试台以为"任务用 `MOVE_CAMERA_TO` 把镜头移到哪个点，那个点就在屏幕 (640, 350)"（`harness.scripted_view`）。V2、V3 成立；V1 的工兵却画在 (640, 376)，低了 26 像素，点击落在他头顶的路面上，所以每次都"没选中"。
  - 证实：同一个包，V1 那一刻按工兵**画出来的位置**点 (640, 378) 就选中了；冰墙落点也按同样偏移点 (634, 299)，冰核马上出现，几秒后冰墙立起（`冰墙V1` = 1）。游戏的放置规则在 V1 落点没拦。
  - 为什么偏（测，`checks/engine_camera.py`，13 个探针）：镜头看的不是脚下的地面高度，旁边有更高的地时它会往上看。V1 南边 40～60 单位有一道高 115（我们的单位）的台地坎，镜头比脚下高了约 43；往北挪 50 到 (1200, 2450) 就只高 2。旁边比脚下低时不往下看（台地坎边上 +4）。直坡中段也会往高处偏（+25）。高 1 个单位，画面上相当于往北挪 0.48 个世界单位（俯角约 52°）。
  - "镜头看多高"的式子是拟合出来的，不是从程序里读的：脚下高度，加上半径 100 内比脚下高出部分的均方根。13 个探针上，画面纵坐标误差都在 12 像素以内，这和平地换算本身的误差一样大（原来的算法最差偏 66 像素）。测试台的世界坐标点击已经改用这个式子（`experimental/testbench/calib.py` 的 `Ground`，`harness.to_screen` / `to_world`），测试 `tests/test_bench_camera.py`。
  - 上轮"换成 V2、V1、V3 也是 V1 失败"那次不算数：那次 V1 一步的截图画的是二号广场（V3）的院子，工兵当时被传到了别处，测试台和任务的时间对不上。
  - **关卡线该怎么改**：关卡、地图、检查都不用改。测试台修好后（上一条），`place` 照原样跑就行。以前在不平的地方"镜头移过去再按世界坐标点"的检查结果要重看：点偏 20 来个单位也可能碰巧放得下，所以修之前的 PASS 只能说明落点附近能放。
