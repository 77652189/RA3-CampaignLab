# 0015 问题按类别从源头修，做的和验的分开，在正式 mod 上验收

**背景**：2026-11-03，用户试玩到第三轮，提出的大多是"不坏"和"看得懂"这两层的问题，例如台词同时播几句、冰墙放不下、车队只走一辆、开场大片黑、矿和矿场的位置不对、土坡难看。其中台词叠播和冰墙放不下这两条，关卡线都报告过"修好、检查全过"，但用户再玩时又出现了。找到的结构原因有五条：
1. 做的线自己写检查，检查的是"我打算做的事做了没有"，而不是玩家实际看到的效果。
2. 检查跑的是测试台的单关 mod，用户玩的是 CampShell，两条构建路径不一样。
3. 为了省额度，规则是"能用数字回答就不截图"，结果看得懂这一层的问题，没人用眼睛看过。
4. 策划线只检查文档，关卡线只把文档里的坐标落进地图，中间没人拿成品去和原版对照。
5. 总控把"修好了"直接转给了用户，没有先核对证据。

用户原话："我想要的解法是怎么样彻底解决问题，而不是打地鼠一样的测试，这样的话其他验收都还是摆设，沦为形式"。

**决策**：
- **每条反馈先归类，再从源头修。** 先回答"这一条违反的是哪条更一般的规则"，然后去改编译器、地图生成器或者设计准则，让这一类错误写不出来，比如台词只有一个排队出口、命令下给整支车队、镜头编译时就限定在可玩区。不在单关里改坐标了事。
- **检查只用来证明源头改法生效。** 检查断言的是这一类问题在所有实例上都成立的规则，不为单个实例补检查。
- **做的和验的分开。** 交给用户之前，先派一个不写代码、不看实现的验收者，拿用户实际玩的正式 mod（CampShell）当玩家来玩：关键时刻截图，按问题类别的清单逐条判断，有一条不过就打回去。
- **只保留一条构建路径。** 验收必须在 CampShell 上跑，测试台的单关 mod 不能当作交付的证据。
- **截图分阶段。** 开发时照旧少截图；验收时截图和看图是必须付的成本。
- **总控转达"修好了"之前，先核对两点**：证据是不是来自正式 mod，是不是用户提的那一类问题。

**后果**：
- 衡量指标：用户的反馈里，有多少条是"已知类别换了个样子又出现"。这个比例应该越来越低。如果又出现，就说明上次是在实例上修的，那一类问题要重新回到源头去改。
- 关卡线修 bug 的方式要改成从源头改，第一次会慢一些，但其余 26 关会一起受益。
- 策划线要把问题类别写进设计准则，以后写稿时就避开这些类别。
- 验收是额外的成本，不过它替掉了用户抓 bug 的时间，用户的试玩只用来判断好不好玩。

**否掉的方案**：
- 把用户的每条反馈都写成一条回归检查：这是打地鼠，只能防同一个实例再出现，挡不住同一类问题换个样子回来，其他验收也会变成走形式。
- 让做的线自己跑一份更长的检查清单：做和验还是同一方，验的还是自己的意图。
- 不改结构，先修完这批再说：按原来的结构，下一轮还会漏。
