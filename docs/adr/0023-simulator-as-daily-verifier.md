# 0023 模拟器管日常验证，测试台管对拍和交付前验收；9 关做到可试玩再一次交给用户

状态：accepted（2026-11-08）。补充 [0022](0022-simulator-before-levels.md) 第 5 条"测试台只做新机制量规则和最后验收"：写明模拟器什么条件下可信、测试台什么时候必须跑、关卡做到什么程度算可试玩。

## 背景

11-08 关卡线给 a1、a3、a6、a7、a8、a9、j7 写了按玩家打法的全程脚本，七关在模拟器里都能打赢，但其中有 5 个机关模拟器根本没实现（升级给的无敌、轨道打击类武器、时停区、对打不动的目标开火、占领命令）。归因：模拟器遇到不认识的东西默默跳过，原来的 win 检查又是脚本替玩家完成目标的快进，把缺口遮住了。所以"模拟器里打赢了"本身不能当证据，要先知道它哪里没覆盖。

用户原话（2026-11-08）：同意"模拟器管日常，测试台管对拍和交付前验收，加对照局"，"写进ADR，试玩攒一批给我"。

## 决定

1. **模拟器可信的三个前提**，缺一条就不能拿模拟器结论当验收：
   - **规则有对拍**：每条规则都有测试台读数的对拍测试，对不上记 strict xfail（照 [0019](0019-port-game-logic-by-layer.md)）。
   - **覆盖可查**：覆盖检查（`experimental/cnv/simcoverage.py`）逐关列出模拟器不认识的武器、升级状态、脚本动作和条件、区域效果、玩家命令；清单只能是登记在案的已知缺口（负责线 + 复现命令），新出现的未登记项让测试变红。模拟器自己把读不懂的项记下来，不再默默跳过。
   - **对照局复核**：挑几关的固定打法，同时在模拟器和测试台上跑，比较结局和关键时间点；每批规则改动后跑一次，结局不同或关键时间差 15% 以上就停下归因。
2. **分工**：
   - 模拟器管日常：调数值、比打法、回归、各关全程脚本，每次提交都跑。
   - 测试台只管两件事：新规则第一次进模拟器时的对拍；每关交给用户试玩前，用巧解的全程脚本在测试台上跑一遍，结局要和模拟器一致。
   - 模拟器原理上测不了的留给测试台截图和用户试玩：画面、字幕与镜头的观感、音乐、手感、AI 的随机感。
3. **一关算"可试玩"的标准**：
   - 该关的覆盖清单清零；
   - 至少 2～3 份全程脚本：题卡设想的巧解能赢；最自然但吃亏的打法明显更难，但不必输；
   - 巧解打完的时长落在目标区间（暂定 8～15 分钟，各关题卡可另定）；
   - 测试台全程验收通过。
4. **试玩攒一批**：9 关都达到第 3 条后，一次性交给用户，每关附一句"考什么"；用户只报觉得不对的地方，反馈按 [0015](0015-fix-error-classes-at-source.md) 归类后从源头修。剧情、对白、过场、配音、美术都在试玩通过之后。

## 否掉的方案

- **模拟器完全代替测试台**：模拟器漏掉的正是它不认识的东西，没有测试台复核就发现不了；画面、声音、手感也测不了。
- **继续每次都用测试台验**：一局几分钟实时、要排队、占显卡，调数值和比打法的轮数上不去。
- **做好一关先给用户玩一关**：打扰次数多，同一类问题会在多关重复出现，攒一批更容易按类修。

## 后果

- 关卡线先做覆盖检查和对照局，再按关补全程脚本；引擎线按覆盖清单补规则。
- 交给用户的时间点往后推到 9 关都达标，中间不发半成品。
