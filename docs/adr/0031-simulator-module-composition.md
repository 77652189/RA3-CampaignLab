# 0031 模拟器改成"物体 = 模块组合"的架构，新功能挂在扩展点上

状态：accepted（2026-11-17）。用户看过总控的根因分析后说："改成模块组合架构，然后派个子agent调研一下"。第 3 条"规则以哪份为准"等调研结果再定。补充 [0029](0029-simulator-layers.md)：0029 的分层和守卫保留，但分层只是把方法分了家，没造出扩展点。

## 背景

用户 2026-11-17 否掉了"重构完再议"五条的权宜办法："我们不能总是重复'野蛮生长——重构——继续野蛮生长'的循环，而是要想想怎么从根源上解决问题"。量到的根因：

- **没有扩展点**：物体是一个 `Body` 类，带 115 个字段，所有部件的状态都在它身上；原版 XML 模块由 `simunits` 的 154 个解析函数读，查询是 `Sim` 上按模板缓存的方法，每帧更新是帧循环里的一格。加一个模块要动 4–5 个中心文件，任何一条线加功能都只能改中心。0029 的搬家把方法分了文件，留下的转调、借用口、世界句柄都是分家后的连接件。
- **同一套规则两份实现**：私有模型 `ra3model/objects/`（heal、body、die、contain……）和公开模拟器 `sim*` 各写一份，注释里有"规则照私有模型"的抄写。
- **结构没有先设计、没有负责人**：每条线照"这周对拍的那项"往最省事的地方加，守卫是事后补的。

## 决定

1. **照原版引擎的结构建内核**：物体 = 一组模块实例；模块工厂按 XML 标签登记，按模板造出模块；每个模块类自带解析好的数据、自己的状态，实现几个固定接口（每帧更新、受伤、死亡、装载等，以程序里的接口为准）；帧循环只推进登记了更新的模块（引擎的休眠 / 唤醒）。加一个 XML 模块 = 新写一个类 + 一个测试，不改中心文件。脚本动作、脚本条件、武器效果、AI 行为也做成按名字登记的扩展点。
2. **端口和适配器**：内核对外只开几个端口（脚本宿主、玩家输入、观测记录、模板数据）；测试台、自动玩家、地图页、私有模型都是接在端口上的适配器，不读内核内部。
3. **规则只留一份**：以私有模型为准、以公开模拟器为准、还是两份同接口互相对照，等调研（两份实现逐部件对比覆盖和差异）后由用户定。
4. **新功能先定扩展点**：动手前回答"它挂在哪个扩展点上"；挂不上就是架构变更，写 ADR、由架构负责人（重构线 R）先设计扩展点再实现。守卫测试只做最后一道网。
5. **迁移用绞杀者模式**：先在旁边搭好框架（物体、模块、工厂、接口、调度），再一个部件一个部件把 `Body` 的字段和 `Sim` 的方法搬进模块类；每一步仍用 0029 的固定任务逐帧记录前后一字不差验收。

## 否掉的方案

- **只做完 0029 的分层再做成包**：方法有了家，但加功能照样要改中心文件，还会再长。
- **"重构完再议"五条的补法**（世界句柄按层收窄、门面名单、接缝测试等）：都在管分家后的连接件，不碰扩展点这个根子。
- **推倒重写**：理由同 0029，行为没法保证不变。

## 后果

- 0029 的 ⑩（做成包）暂停，包的布局按新架构重新设计；已做的分层不白做，逻辑已按部件归好堆，是搬进模块类的原料。
- "已对拍"的标准不变；逐帧记录仍是每一步的验收。
- 恢复各引擎线之前，"新规则放哪个文件"指南要改写成"挂在哪个扩展点上"。
